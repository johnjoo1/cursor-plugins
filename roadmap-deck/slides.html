Data Monitoring and Quality

First Responder

Humans shouldn't be the first to look at an alert. AI should.

01

Judge

  • Assess severity, and whether the alert is even real
  • Run initial investigations automatically
  • Score priority against your defined runbooks

02

Investigate

  • Trace to root cause using all available context
  • Pull lineage, check history, query live data
  • Cross-reference prior resolved issues

03

Act

  • Ignore it — noise, or a false positive
  • Escalate to a human with full context attached
  • Open a ServiceNow or Jira ticket automatically

Incidents are the envelope

Every action the agent takes lands inside an incident — grouped across checks, tables and days using lineage and documentation; silenced and auto-resolved where severity and past triage notes say it's noise; routed to the right human when it isn't.

Appendix · Data Monitoring and Quality

It follows your runbooks. Not a generic one.

Where First Responder's context and instructions live.

Context

What the agent knows

  • Documentation at both the domain and the table level
  • The data itself, and column-level lineage across it
  • AIDA memories — everything the platform has already learned about your data
  • Prior incidents, and how they were resolved

Instructions

What the agent is told to do

  • Define multiple agents, each applied at the notification-channel level
  • Override the general instructions at the individual check level
  • Incident properties you control — custom statuses, incident types and tags

The trade-off we're managing here is flexibility versus clarity — enough control to encode how your team actually works, without a configuration surface nobody wants to maintain.

Appendix · Data Intelligence

How an Autopilot job is defined

And why it lives in Data Intelligence rather than Monitoring.

Subject

What should the agent look at?

→

Selection

Which tables, checks or domains?

→

Fan-out

One report covering all, or one per item?

→

Trigger

On a schedule, or when the data lands?

Triggers watch your data, not the clock

Run when all the tables are fresh, or run per table the moment that table is fresh — subject is the table, selection is the checks on it, one run per table. A cron job fires whether the data arrived or not.

Reactive versus proactive

First Responder answers failures nobody asked for — that's why it sits in Monitoring and Quality.

If someone asks why a freshness-triggered agent isn't monitoring: the check that noticed is monitoring. What Autopilot adds is the written analysis on top of it.

Anomalo's own data, without the pipeline

Batch exporter results become native tables — context any agent can look up.

Today

  • Anomalo exports results to your object store
  • You build and maintain a pipeline into the warehouse
  • You model the tables yourself
  • Only then can you query your own quality history

This quarter

  • Check results, incidents and metadata are native tables
  • Queryable from inside Anomalo on day one
  • No S3 hookup, no pipeline, no modelling work
  • Available to AIDA, Autopilot and your own reporting

First Responder, Autopilot and AIDA can all read these the same way they'd read a data catalog. That's why it's context, not reporting — and it's why one of the least glamorous items this quarter is also one of the most requested.
